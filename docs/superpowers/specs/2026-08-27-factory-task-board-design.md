# 牛马工厂全局任务看板设计

**日期：** 2026-08-27  
**状态：** 已与用户对齐，进入实现  
**目标：** 在牛马工厂中提供一套人类与正式员工共同维护、全工厂共享、按项目筛选、可即时或定时派活的任务看板。

## 1. 产品语义

### 1.1 一套全局看板

- 工厂只维护一套任务总账，不为每个项目创建孤立看板。
- `project` 是任务字段，也是筛选条件；默认展示所有项目。
- 默认展示所有未归档任务和这些任务实际使用中的全部状态。
- 已归档任务默认隐藏，可显式筛选查看。

### 1.2 人类状态是自由文本

- 每个任务直接保存 `status`，例如 `TODO`、`设计中`、`进行中`、`待验收`、`完成`。
- 不设置“正式状态 / 临时状态”两套概念，也不要求先注册状态。
- 人类或员工把任务改到一个新状态时，该状态立即成为看板列和筛选项。
- 当前结果集中没有任务使用的状态不展示；重新出现时自动恢复。
- 看板提供常用状态的稳定排序（TODO → 进行中 → 待验收 → 完成），其他状态按首次出现顺序排列，但排序元数据不是状态存在的真相源。

### 1.3 展示状态与执行状态分离

- `status` 面向人类，完全自由。
- `execution.state` 面向调度器，固定为：
  - `idle`：没有待执行计划；
  - `scheduled`：等待触发时间；
  - `dispatching`：已获得调度租约，正在创建派活请求；
  - `queued`：Pi 已接收派活请求或 job 正在排队；
  - `running`：员工 job 正在执行；
  - `succeeded` / `failed` / `cancelled`：本次执行终态。
- 拖动看板卡片只改变人类状态，不隐式启动任务。
- “指派并执行”“立即执行”或到达 `triggerAt` 才触发执行。

## 2. 任务模型

每个任务至少包含：

| 字段 | 说明 |
|---|---|
| `id` | 稳定任务 ID |
| `title` | 简短标题 |
| `description` | 任务正文 |
| `context` | 可长期保存的背景、约束和交接信息 |
| `project` | 项目筛选键，可为空 |
| `status` | 自由的人类可见状态，默认 `TODO` |
| `assignee` | 当前负责的正式员工，可为空 |
| `creator` / `updatedBy` | 来源留痕，空值按用户处理 |
| `priority` | `low` / `normal` / `high` / `urgent` |
| `labels` | 自由标签数组 |
| `triggerAt` | 可选的一次性触发时间，ISO 8601 |
| `mode` | 派活语义：`auto` / `queue` / `steer` / `now` |
| `parentTaskId` | 子任务关联；拆分出的任务可独立指派 |
| `archivedAt` | 归档时间；归档和完成分离 |
| `execution` | 调度租约、request/job 链接、结果和错误 |
| `revision` | 乐观并发版本，避免 Web 拖动覆盖员工刚写入的更新 |
| `createdAt` / `updatedAt` | 时间留痕 |

任务详情返回事件时间线和直接子任务。结果证据以 linked request/job、结果摘要和事件记录呈现，不复制完整 job 流。

## 3. 存储与一致性

- 使用现有 local-first 约定，在 `workersDir/factory-tasks.jsonl` 追加事件。
- 读取时折叠事件生成任务快照；运行数据不进入 Git。
- 每个任务写入前使用 `workersDir/.locks/factory-tasks/<task-id>.lock` 的 `open(..., "wx")` 原子锁。
- 所有更新递增 `revision`；API 和工具可传 `expectedRevision`，冲突时拒绝而不是静默覆盖。
- 事件保留 actor、时间、patch 和执行链接，支持审计与恢复。

## 4. 派活与定时调度

### 4.1 同一条正常执行链路

1. Web / 工具先创建或更新任务。
2. 需要执行时，调度器为任务创建唯一 `executionKey` 并取得短租约。
3. 调度器创建现有 `worker-task-request`，附带 `factoryTaskId` 和 `executionKey`。
4. Pi 主进程沿现有 `work:assign` 权限检查和 `enqueueWorkerCommand` 路径启动员工 job。
5. request 接收、job 启动、job 结束时回写任务的固定执行状态和证据。

因此即时派活、Web 定时派活与直接对话使用相同的员工 session、cwd、后端和队列语义，不调用 OS cron，也不启用旧 runner 环境。

### 4.2 幂等和恢复

- 同一个执行周期只有一个 `executionKey`。
- 创建 request 前后都按 `executionKey` 检索，进程在中间崩溃也不会重复创建派活请求。
- `dispatching` 持有有限租约；租约过期且没有终态证据时可恢复。
- Web server 启动后先等待 grace period，再加随机 jitter 扫描到期任务。
- 每轮只处理小批量任务；过期任务按触发时间排序缓慢恢复，避免设备刚启动时任务风暴。
- 第一版只支持一次性 `triggerAt`。周期任务继续由现有定时任务机制管理，后续若统一重复调度再另行设计。

### 4.3 显示状态自动化边界

- 系统执行成功会记录 `execution.state=succeeded`，失败记录 `failed`。
- 系统不强制覆盖人类的 `status`，避免把 `待验收`、`等待上线` 等业务阶段错误改成 `完成`。
- 员工提示词明确要求在工作推进时调用任务更新工具；人也可在 Web 拖动或编辑。

## 5. Agent 工具

- `factory_task_create`：创建任务，可只建卡，也可带 assignee 和执行时间。
- `factory_task_list`：按项目、状态、员工、归档和文本查询全局任务。
- `factory_task_get`：查看详情、子任务、执行证据和事件。
- `factory_task_update`：更新状态、上下文、负责人、触发时间等；新状态无需注册。
- `factory_task_split`：从父任务拆出多个可独立指派的子任务。
- `factory_task_archive`：归档或恢复。
- `factory_task_run`：立即为已指派任务发起一次执行。
- 兼容现有 `factory_task_assign`：改为“创建看板任务 + 走正常派活”，并继续返回 request/job 结果。

当 actor 给其他员工指派执行时继续检查现有 `work:assign` 权限。查询和更新共享任务不新增一套割裂权限系统。

## 6. Web 体验

### 6.1 页面结构

- 左侧导航新增“任务看板”，`#/tasks` 展示全局看板。
- 顶部提供：新建任务、搜索、项目、员工、状态、优先级、执行状态、归档筛选和刷新。
- 看板列来自当前过滤结果中任务的真实 `status`；默认全部展示。
- 卡片展示标题、项目、负责人、优先级、标签、触发时间和执行状态。
- 桌面端支持拖放改状态；键盘和移动端可在详情表单中选择或输入新状态。
- 详情抽屉支持编辑、立即执行、拆分、归档/恢复，并展示上下文、父子任务、request/job 链接和事件时间线。

### 6.2 交互与可访问性

- 拖动采用乐观 UI，但服务端 `revision` 冲突时刷新并提示。
- 所有关键操作都有明确 loading/disabled/error 反馈。
- 按钮保证可见 focus 状态和足够点击区域；颜色不是唯一状态提示。
- 遵循当前牛马工厂视觉变量，不引入阻塞 Web Font 或第三方拖拽库。
- 大量任务通过服务端筛选、默认上限和按列渲染控制 DOM 数量；筛选请求防抖。

## 7. 兼容性与非目标

- 保留 `/api/task-requests` 和旧派活请求详情，作为底层执行审计；不删除历史数据。
- 项目实体中的旧 `todos` 保持只读兼容，不自动迁移，避免改变已有项目文档语义。
- 不把看板实现成 Goal；Goal 是单员工长期目标，本看板是跨员工、跨项目的人机协作总账。
- 不重载插件、不修改宿主 `workersDir` 真实数据来做测试；所有测试使用临时目录和独立 Web server 端口。

## 8. 验收标准

1. 人或员工可创建、查询、编辑、拆分、归档和恢复任务。
2. 任意新状态字符串可直接形成列和筛选项；默认显示全部现存状态。
3. Web 可按项目查看全局任务，并能拖动卡片改状态。
4. 即时指派产生且只产生一个派活 request；忙碌员工沿现有 queue/steer 语义处理。
5. 定时任务到期后由 Web 内进程缓启动扫描，并通过同一 request/Pi job 链路执行。
6. 重启或租约过期恢复不会对同一 `executionKey` 重复派活。
7. request/job 结果可在任务详情中追踪；执行终态不覆盖自由的人类状态。
8. `pnpm run check`、`pnpm test` 全部通过，独立临时目录 HTTP 冒烟通过。
